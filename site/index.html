FastAPI · Strapi · Meilisearch

Keep a search index in step with Strapi, one webhook at a time.

Strapi can tell you when an entry changes, but it will not keep Meilisearch up to date for you. I wrote a small service that takes those webhooks, picks and renames fields from a YAML file, and writes the result to Meilisearch or to a URL of your choice. Duplicate and out-of-order events do not overwrite newer content.

Map your content type

Describe one Strapi content type and get the mapping.yaml block for it. This runs in your browser and sends nothing anywhere. The same rules as the hub's loader are applied, and a test feeds this script's output to that loader.

The model value in the webhook payload.

Used as GET /api/<path>. Leave empty to reuse the index name.

Strapi 5 uses documentId. Strapi 4 only has id.

One per line. name keeps the name, source: target renames it.

    content_types:
  article:
    index: articles
    api_id: articles
    id_field: documentId
    fields:
      title: title
      slug: slug
      body: content
      publishedAt: published_at

    To map more than one content type, add the extra blocks under the same content_types key.

    What works

    This is the state of main. Everything marked "works" is covered by tests that run without a network.

    • works Receiver for entry.create, update, publish, unpublish and delete, with a shared-secret header compared in constant time
    • works YAML mapping with field selection and renaming. Errors name the content type and field.
    • works Meilisearch and JSON webhook targets. Upserts compare updatedAt, so a repeat or an older event is skipped.
    • works Retries with exponential backoff, then a JSONL dead-letter file
    • works Dry run, and a reindex command that pulls published entries from the Content API
    • partial Contract tests use payloads I wrote from the Strapi docs. They have not been recorded from a running Strapi.
    • partial The Docker Compose demo uses a small Strapi-shaped stand-in, not a real Strapi.
    • not done Dead-letter replay, tombstones for deletes, waiting for Meilisearch tasks to finish, and a PyPI release

    Quickstart

    Settings come from environment variables and are checked at startup. A bad value stops the process and lists everything that is wrong. Dry run logs what would be written and never calls Meilisearch, so you can try this without one running. 

    git clone https://github.com/mohamedtaqysalmi/strapi-sync-hub
cd strapi-sync-hub
python -m venv .venv && . .venv/bin/activate
pip install -e .
cp mapping.example.yaml mapping.yaml
export STRAPI_SYNC_SECRET="replace-with-16-or-more-characters"
export STRAPI_SYNC_TARGET=meilisearch
export MEILISEARCH_URL=http://localhost:7700
export STRAPI_SYNC_DRY_RUN=true
uvicorn --factory strapi_sync_hub.main:create_app_from_env

    In Strapi, add a webhook that points at /webhook, add a header X-Sync-Secret with the same secret, and tick the entry events you want. Settings for a real Meilisearch, and the reindex command: 

    STRAPI_SYNC_SECRET=...
STRAPI_SYNC_TARGET=meilisearch
MEILISEARCH_URL=http://localhost:7700
MEILISEARCH_API_KEY=...
STRAPI_SYNC_MAPPING=mapping.yaml
STRAPI_SYNC_MAX_RETRIES=3
STRAPI_SYNC_DEAD_LETTER_PATH=dead-letter.jsonl
    export STRAPI_URL=http://localhost:1337
export STRAPI_API_TOKEN=...
strapi-sync-hub reindex --dry-run
strapi-sync-hub reindex --content-type article

    The Compose demo in demo/ starts Meilisearch, the hub and the stand-in CMS.

    How it works

    The secret is checked before the body is read. Drafts are skipped, unpublish and delete remove the document, and everything else is written with the entry's updatedAt stored beside it. A write that is not newer than what the target holds is dropped. If the target keeps failing, the event is appended to the dead-letter file and the webhook answers 200 so Strapi does not keep retrying. 

    Strapi webhook ── X-Sync-Secret ──► verify
                                      │
                                      ▼
Content API ◄── reindex CLI ──►   map from YAML
                                      │
                                      ▼
                             retry with backoff
                               │            │
                            ok │            │ attempts used up
                               ▼            ▼
              Meilisearch or JSON webhook   dead-letter.jsonl

    How I built it

    The mapping lives in YAML

    Content types change in the CMS more often than the service does. Keeping the field list out of code means a rename does not need a release. The cost is that a missing field is skipped quietly, so you only notice when a search comes back empty.

    Idempotency from a stored timestamp

    Every document carries the updatedAt it was built from. That avoids an outbox table, but the check is a read followed by a write, so two simultaneous deliveries for one document can still race.

    Park failures instead of failing the webhook

    After the retries are used up the event goes to a JSONL file and the hub answers 200. Losing the payload seemed worse than a quiet file. There is no replay command yet, so someone has to look at that file.

    A stand-in instead of a full Strapi in the demo

    Bootstrapping a real Strapi with an admin user and content types is a lot of setup for a demo, so the Compose file runs a small stand-in that speaks the same envelope. That is why the contract tests are labelled as written from the docs.

    Limits and roadmap

    • An update that arrives after a delete can bring the document back, because deletes are not recorded.
    • The webhook target remembers the newest updatedAt in memory only, so a restart forgets it.
    • A 202 from Meilisearch means the task was queued. The hub does not wait to see it succeed.

    Open work is in the issue list. To help, start with CONTRIBUTING.md.
